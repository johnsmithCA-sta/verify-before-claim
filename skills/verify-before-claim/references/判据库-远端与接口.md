# 判据库 · 远端与接口（26 条）

> 用法同《判据库-本机与工具链》：**现象 → 判据 → 反例**，反例必须能跑出 FAIL。
> 归类编号对应 SKILL.md 的六类失败形态表；第 6 类（**探测失败 ≠ 对象不可用**）集中在本文件 R14–R21。

## 类 4 · HTTP 200 ≠ 正确内容（R01–R06）

### R01 错误页也是 200
- **现象**：下载接口的签名偶发失效，返回体是一段错误 XML（约 542 B），**HTTP 状态码仍是 200**。只看状态码或只看退出码（`$?` = 0）会把错误页当文件比对，进而把 4,634 B 的真文件判成「平台只有 542 B」。
- **判据**：下载后先看**响应体开头**——不是预期格式即判失败，重新取链接；文件名 / 字节数 / 内容三者都要对。
- **反例**：故意用一个无效签名请求同一接口 —— 它同样返回 200，此时若你的校验仍报「下载成功」，即证明状态码不可作判据。

### R02 对象存储签名的前导斜杠
- **现象**：上传链路某一步报签名不匹配（403）。真因是签名对象键必须带**前导斜杠**，直接用返回的键原值签名必失败。
- **判据**：403 时先读响应体里回吐的待签字符串，**逐字节比对**与本地构造的差异，而不是先怀疑凭据无效。
- **反例**：同一对象分别用「带前导斜杠」与「不带」两种键签名 —— 只有一种通过，即可定位到本判据。

### R03 签名窗口的起点在未来
- **现象**：拿到上传凭证后**立刻**发起请求报「凭证无效」，被读成权限 / 凭据坏了。实际返回的授权串里时间窗口起点约为申请时刻 **+120~180 秒**（防时钟漂移）；在窗口开始前调用必然失败，且**每重新申请一次，起点又往后推约两分钟**。
- **判据**：把窗口起点换算成本地时间，晚于当前时间就是「还没生效」——**等过去再发**，最省事；不要反复重申请。
- **反例**：记录一次窗口起点，`sleep` 越过它再发 —— 从失败变成功即证明前一次失败与凭据无关。

### R04 前端是纯单页应用 ⇒ 状态码不能验链接
- **现象**：某平台网页端是 SPA，**任何路径都返回 200**（包括不存在的资源）⇒ 用请求状态码验证「某个深链是否存在」**恒为真**，得不出任何结论。
- **判据**：验证资源存在改用**数据接口**（返回结构化列表）或实际调用（能否安装 / 下载）；不把猜测的深链写进对外文档。
- **反例**：拼一个**必然不存在**的路径请求同一站点 —— 仍返 200，即证明该判据无效。

### R05 接口返回的「链接字段」是构造值
- **现象**：接口返回体里的主页字段看着像一个可访问 URL，实际直接请求返回 405——**它是拼出来的，不代表存在可用页面**。
- **判据**：任何要写进对外文档的链接，**先亲自请求一次**确认它可用；用「调用命令」这类可复制、可执行的文本替代不可靠深链。
- **反例**：对该字段值直接发起请求 —— 非 2xx 即证明它是构造值，不可对外。

### R06 官方文档给的地址命名规则不可信
- **现象**：按文档的命名规则拼服务地址，长期连不上；真实地址形态是「账号 ID + 随机串 + 地域」，**只能从接口返回里读**。
- **判据**：地址 / 端点 / 域名一律以**接口或控制台的实际返回**为准，文档规则只作理解用。
- **反例**：把「按文档拼出的地址」与「接口返回的地址」并列请求 —— 两者不等价即证明不能拼。

## 类 5 · 元数据 ≠ 实体（R07–R13）

### R07 列表接口的体积字段是缓存
- **现象**：覆盖上传后，列表接口的 size 字段**仍显示旧值**（时间字段是新的），据此判「没生效」或「已生效」都会错。
- **判据**：判是否真的替换，**只能下载实体**：比字节数 + 检索只有新版才有的标记串。
- **反例**：上传一份内容必然变化的文件，上传后立刻读列表里的 size —— 若它没变，即证明该字段不能用于本次判定。

### R08 批量操作会刷平时间字段
- **现象**：批量移动 / 批量修改会把整批条目的更新时间**刷成同一分钟**，于是「谁更新」这个判断彻底失效（不同批次各自被刷平）。
- **判据**：判内容新旧**回读正文做指纹比对**（长度 / 字数 / 章节结构 / 关键串），不看时间字段。
- **反例**：对两个**内容不同、时间被刷平**的条目跑你的新旧判定 —— 判不出即证明判据错。

### R09 「已上架」不能只看名称能搜到
- **现象**：检索命中只说明平台上**有这个名字**，不说明平台上的是你手上这一版；提交后本地继续改不会自动同步。实测出现过平台包与本地包体积差 10 KB、且恰好缺三样针对性的防线。
- **判据**：把平台包**拉下来逐文件比对**：哈希 + 字节数 + **章节结构**（标题列表最直观）三方。
- **反例**：拿一个**刚新增、尚未提交**的章节标题去平台包里查 —— 查不到即证明你在比对本地；查得到才是真上线。

### R10 访问统计只保留固定天数
- **现象**：流量接口只保留约两周，不落盘则历史**永久丢失、无法环比**。
- **判据**：周期性存档（周存档最省事），把归档当唯一历史源。
- **反例**：取一次两周前的数据 —— 取不到即证明不落盘就没有历史。

### R11 「本地是源稿所以领先」是错的假设
- **现象**：默认本地文档是「源」、线上是「旧版」，于是不做比对直接推送。实测真撞过**线上已含第二轮实证、而本地源稿还停在上一节**的情况。
- **判据**：上传前**回读线上最新版做指纹比对**（去格式标签后逐句查本地是否命中）；未命中的句子分三类：已被证伪的旧结论（不回带）/ 线上维护注记（吸收）/ 版本与标题差异（正常）。
- **反例**：把线上正文去标签后与本地逐句比对 —— 若存在**本地没有、也不属于上述三类**的句子，即证明本地落后。

### R12 被保护规则锁定的标签：打标前必须冻结产物
- **现象**：标签一旦受「禁止删除 + 禁止强推」规则保护，发布后要改内容**无解**，只能靠后续提交追平，标签永远停在旧提交。
- **判据**：打标**之前**把所有产物冻结到位（含所有自动生成的报告文件），先确认「远端是否已有该版本的标签」，再打。
- **反例**：对已存在的标签尝试重指 —— 被规则拒绝即证明该标签不可变，此刻才发现等于返工。

### R13 精准部署前的三方哈希核对
- **现象**：远端可能存在人工校改，本地可能落后；凭记忆列「本次改了哪几个文件」会造成漏传或覆盖（实测以为只有 2 个漂移文件，实际第 3 个同样会被一次全目录部署静默覆盖）。
- **判据**：部署前比对**远端 / 本机工作树 / 版本库 HEAD** 三方哈希，一次性回答「远端有没有人工校改」「本机是否落后」；据此选「只传本次改动」且**不带删除选项**。
- **反例**：先只比本机与远端（少比 HEAD 一方）—— 若仍有差异解释不了，即证明三方缺一不可。

## 类 6 · 探测失败 ≠ 对象不可用（R14–R21）

> 本族共同口径：**探测手段的失败，不能推断被探测对象的状态**。判定「不可用」之前，必须先证明探测手段在该环境下**具备可用性**。

### R14 某些 shell 没有 `/dev/tcp` ⇒ 端口探测恒判 CLOSED
- **现象**：用 `/dev/tcp/host/port` 做端口探测，在该类 shell 下**静默失败、恒判 CLOSED**——据此曾误判「服务全挂」，实际端口一直在正常服务。
- **判据**：端口可达性改用请求工具的返回码（`000` 才是真不通）或系统的监听列表命令；`/dev/tcp` 只写在显式声明 bash 的脚本里。
- **反例**：对一个**确定在监听**的端口跑 `/dev/tcp` 探测 —— 判 CLOSED 即证明探测手段失效，其此前的所有 CLOSED 全部作废。

### R15 进程管理器的列表命令在受限环境里看不到目标服务（假阴性）
- **现象**：轻量列表命令在工具沙箱内**看不到目标服务**，看起来「服务没注册」，实际它跑得好好的；换用**带用户域详情的查询命令**才能看到。
- **判据**：状态查询用能展开用户域的查询形式；顺带注意该环境下的检索不支持某些正则简写，会静默零命中。
- **反例**：先用列表命令查，再用详情查询命令查**同一个**服务 —— 前者空、后者有，即证明列表命令是假阴性来源。

### R16 用前端请求的成败当可达性判据 ⇒ 误报「服务没在跑」
- **现象**：页面加载时先发一个探测请求，不通就弹「服务未运行」；而**探测本身被环境拦截**、新窗口被拦截也弹同一个提示 ⇒ 两类完全不同的故障合并成一个错文案。
- **判据**：**直接尝试打开**，把「打不开」与「服务不在」分开报；探测失败不等于服务不可用。
- **反例**：在探测必定被拦截的环境里跑一次 —— 提示仍是「服务未运行」而服务健康，即证明该判据误报。

### R17 启动应用后需要等待监听就绪
- **现象**：启动本地应用后**立刻**探测端口，连返两个「不通」，判「起不来」；实际约 10 秒后才开始监听。
- **判据**：启动类操作后留出就绪窗口再探测（或轮询到就绪为止），探测一律绕过本地代理直连。
- **反例**：记录「启动时刻」与「首次监听时刻」—— 两者相差数秒即证明「早探 = 失败」是探测时机问题。

### R18 有鉴权的缓存服务不能用 ping 命令探活
- **现象**：对要求认证的实例执行常规 ping，直接返回认证错误 ⇒ 被读成「服务异常」，实际服务正常。
- **判据**：探活降级为**只探 TCP 连通**（建连成功即可）或带认证后再 ping。
- **反例**：分别跑「ping」与「只建连」—— 前者报认证错误、后者成功，即证明失败来自探测方式。

### R19 整个域名临时不可达，而其他域名正常
- **现象**：某域名的 443 全部超时，**DNS 解析正常**，同时其他域名（代码托管、搜索、地图等）全部正常 ⇒ 非全局网络问题、非 DNS 问题；约 40 分钟后自行恢复。连带症状：采集耗时从 10 秒暴涨到 240 秒（逐层重试耗尽），且兜底路径把数据静默写成 0。
- **判据**：先**复测确认是否自愈**，不要急着改代码或换数据源；依赖该域名的脚本必须遵守「空即失败」。
- **反例**：同一时刻对两个域名各发一次请求 —— 只有一个失败即证明是单域故障，不是本机网络。

### R20 「网页打不开」与「接口不可用」不等价
- **现象**：网页超时，据此判「站点整体不可达」；实际接口域名与代码传输通道**全部正常**——受影响的只有浏览器打开网页这一件事。
- **判据**：按**域名分别探**；需要网页侧操作时走移动网络 + 官方入口，镜像站只用于查文档，**禁止在其上登录或建凭据**。
- **反例**：网页失败的同时请求接口域名 —— 返回正常即证明「全不通」的结论过宽。

### R21 「又连不上」常是本地会话态不持久
- **现象**：SSH 报权限拒绝，被读成「通道坏了 / 主机不可达」；真因是**本地凭据代理的会话态在重启或超时后清空**，且没有任何自动加载 ⇒ **每个新会话的第一次连接都必须重新加载**。
- **判据**：连接前统一调一次「确保凭据已加载」的入口（判断依据用**公钥指纹**，不要用会变的注释字段）；加载失败即退出，不带着空会话继续跑分支。
- **反例**：同一会话内连续两次连接 —— 第一次失败、加载后第二次成功，即证明失败在本地会话态而非远端。

## 类 3 · 退出码 0 ≠ 成功（远端侧，R22–R23）

### R22 远端缺少某个 CLI 而错误被重定向吞掉
- **现象**：远端没有该命令行工具，`… 2>/dev/null` 把「命令不存在」的非 0 退出码吞掉 ⇒ 输出为空，看起来像「这个表里没数据」。
- **判据**：远端读结构化数据一律走**解释器内建能力**（`python -c` 之类）而非依赖 CLI；在判定「没数据」之前，先验证工具本身存在。
- **反例**：先跑一次「工具是否存在」的探测 —— 不存在即证明此前所有空结果都是工具缺失，不是数据为空。

### R23 定时任务执行的是绝对路径，可能不在项目目录
- **现象**：项目目录里的脚本被反复记为「未部署的待办」；实际定时条目指向的是**另一个绝对路径**，且线上那份比项目内那份**还新一版**。把项目内那份「部署」过去**也不会被执行**。
- **判据**：先看**定时条目的实际执行路径**，再看两端哈希；差异只在注释或版本说明时，说明它是**快照，不是待部署品**。
- **反例**：改一处只在项目内那份存在的标记，然后等一次周期 —— 线上产物无变化即证明执行的是另一个路径。

## 巡检与口径（R24–R26）

### R24 健康巡检扫日志的三大误报源
- **现象**：① 报告正文 / 分析措辞混入被当成错误关键字；② **计数为 0**（`errors=0` / `failed=0`）命中错误关键字；③ 正常降级（某数据源失败但程序收敛出结果）被当故障。
- **判据**：三层过滤——**只扫程序状态行**（时间戳行 / 标签行 / 异常栈 / 分隔线 / 命令回显）、**剔除零计数片段**、**降级信息不进健康检查**。并明确巡检口径边界：只报「任务有没有跑 + 日志有没有程序级错误」，不报业务与数据质量。
- **反例**：构造一份**只含 `errors=0`** 与一段分析措辞的日志 —— 按你的规则应报 0 个错误；若报出错误，即证伪。

### R25 用「日志相邻行」判远端任务成败
- **现象**：某次运行的确认行在日志里**不见了**，一度判为「失败但报了成功」。真因是**输出缓冲错位**——父进程块缓冲、子进程直写，子进程的确认行被排到父进程该次运行的若干行**之前**（症状 =「本次缺一行、上次多一行」）。所有父子进程混合输出的日志都有此现象。
- **判据**：判据改成**计数**：确认行数 == 全链路完成行数 ⇒ 全部成功；不看某一行在不在。
- **反例**：对同一批日志分别用「找某一行」与「计两种行数」两种方法 —— 前者给出矛盾结论、后者自洽，即证明前者不可用。

### R26 「0 次触发」的二义
- **现象**：某护栏 / 开关连续多批「触发 0 次」，被解读成「今天环境不满足条件」；真因是它的**入参恒为空**（上游一个开关把输入关掉了）⇒ **护栏是死代码**。同类：日志里有 17 次同名标签命中，却来自**另一个上下文块**，与本品无关。
- **判据**：验收任何护栏 / 开关**先证它的输入非空**（一条独立查询），再看触发次数；同名命中还要看它上方数行的**上下文标题**确认来源。
- **反例**：用一条独立查询取该护栏的入参 —— 取到空即证明「0 次触发」的原因是读不到输入，不是条件不满足。
